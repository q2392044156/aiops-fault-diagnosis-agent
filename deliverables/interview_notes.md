# AIOps 故障诊断 Agent 面试说明

## 30 秒介绍

这是一个从 1117 万行 HDFS 日志开始的端到端 AIOps 项目。我先做了可追溯的数据协议和时间隔离，再比较 LR 与 LSTM，冻结轻量 LR 作为默认模型；之后实现 BGE ONNX 混合检索、DeepSeek 证据约束报告和确定性单 Agent。系统所有工具只读，报告必须引用证据，任何高风险或不确定情况都转人工复核，批准也不会执行动作。最终 40 个独立案例做了三次真实在线评测，并在全新 Conda 和隔离 Docker 环境完成复现。

## 适合强调的工程决策

- 不用随机切分日志，而是按时间、关联组和 embargo 控制泄漏。
- LSTM AP 更高但固定阈值 F1 没有稳定提升，默认选择更简单、更可部署的 LR。
- Dense 模型导出 ONNX，线上镜像不装 Torch/CUDA。
- LLM 不负责工具自由规划；W9 实测可选路由只有 55%，所以关闭并保留确定性状态机。
- 调用前原子预留预算；崩溃后保守结算，避免重复付费调用。
- 审批绑定 report hash、revision 和 action IDs，批准报告不等于执行动作。

## 三种行业表述

### 数据平台 / 大数据运维

针对 HDFS block 会话构建异常检测与只读诊断链路，强调数据追溯、时间泄漏控制、NameNode/DataNode 证据和安全停止条件。

### 云平台 / SRE

强调可恢复任务、租约、幂等、审计、预算、健康检查和风险转人工；当前 SQLite 单 worker 是研究原型，不冒充多机高可用。

### AI Agent / LLM 工程

强调检索、引用白名单、严格 Schema、坏 JSON 修复/降级、prompt injection 防护和真实成本评测；说明为什么没有采用“让模型自由调用工具”。

## 简历描述示例

- 基于 1117 万行 HDFS 日志构建可复现的会话级异常检测管线，冻结 TF-IDF+LR 与 LSTM 对照协议，并完成一次性时间外测试。
- 搭建 30 篇原创运维知识库和 BM25/BGE-ONNX/RRF 混合检索，Rtest Top-3 Recall 0.975、MRR 0.9375。
- 实现证据约束 DeepSeek 报告与可恢复单 Agent，覆盖预算预留、人工复核、幂等和安全降级；120 次独立在线案例中强制复核 Recall 与引用合法率均为 100%。
- 将 API、worker、Streamlit 拆分为 CPU-only Compose 服务，采用非 root、只读根文件系统、只读制品/Secret 和 SQLite 租约恢复。

## 常见追问

**为什么 LR 做默认模型？**
LSTM 的 AP 明显更高，但测试 F1 仅与 LR 持平，且没有跨 seed 的稳定优势；LR 更轻、更易审计、CPU 性能更好。选择规则在看测试集前冻结。

**0.88 的测试 F1 是否退步？**
验证集接近 1.0，但时间外测试降到约 0.883，说明明显分布漂移。这正是时间切分和一次性测试的价值，不能用验证结果冒充泛化性能。

**Agent 为什么不用 LangGraph 或多 Agent？**
问题规模不需要。自定义状态机更易冻结节点、预算、租约和审批语义；W9 真实评测还证明自由路由不够可靠。

**如何防幻觉？**
只能引用当次检索允许的 chunk ID；无证据不调用；Schema/引用校验失败最多修复一次；再失败使用可审计模板。只能说降低风险，不能声称“无幻觉”。

**审批会执行操作吗？**
不会。所有 ActionAdvice 的 `execution_allowed=false`，数据库和 API 没有动作执行入口。

**下一步如何生产化？**
需要真实工单/根因标签、跨集群验证、企业身份与 TLS、外部数据库/队列、多副本和容量压测；不能直接把当前单机原型称为生产系统。

## 禁止夸大

- 不说“根因准确率 100%”或“自动修复”。
- 不把 block 标签称为真实故障事件或根因。
- 不把本机吞吐称为生产容量。
- 不把验证集 0.999 指标称为测试泛化能力。
- 不说“完全没有幻觉”；只能说明引用与降级门禁通过。
- 不说具备企业级鉴权、高可用或跨系统泛化。
