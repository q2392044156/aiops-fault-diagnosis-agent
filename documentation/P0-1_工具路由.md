# P0-1：受控工具路由（function calling）实施报告

> 目标：把 `query_metrics` 从"永远返回 not_available 的桩"变成真实指标查询，用 function calling 重写工具路由，并用 30 例对照实验量化三种策略的差异。
> 结论：**规则质量是主要收益，function calling 的价值在参数与接口安全，不在准确率。** 默认仍保持确定性路由，v2 作为可选能力。

---

## 1. 原来的问题

旧路由有三个结构性问题，导致"55% 准确率"这个数字其实没有多少解释力：

1. **工具本身没有信息量**：`query_metrics` 是静态桩，永远返回 `not_available`，模型调不调都一样；
2. **只给名字不给参数**：旧路由输出 `{"next_tools": [...]}`，参数要在下游猜；
3. **没有校验**：模型可以返回任意字符串，错了也只能靠预算兜底。

## 2. 实现内容

| 文件 | 职责 |
| --- | --- |
| `platform/metrics_store.py` | 读取 CSV/JSONL 指标，按主机 + 时间窗聚合（min/max/mean/p95/last + 采样点） |
| `diagnosis/tool_specs.py` | 三个只读工具的 JSON Schema、优先级与参数校验 |
| `diagnosis/router_v2.py` | `ToolRouter`：白名单、去重、数量上限、Schema 校验、失败回落 |
| `knowledge/generation/client.py` | 新增 `complete_tool_calls`，复用原有重试、超时与预算结算 |
| `diagnosis/engine.py` | `_route` 支持 v1/v2 切换；`_llm_tools` 计入 LLM 预算；摘要里的 `metrics_available` 改为真实探测 |
| `evaluation/router_eval.py` | 准确率、精确/召回/F1、多余/漏调率、成本指标与 Markdown 表格 |
| `ops/scripts/evaluate_router.py` | 四模式对照实验入口 |
| `resources/evaluation/router/cases.jsonl` | 30 个案例 |

关键设计：

- **模型只负责选择，是否允许由程序判定**：未知工具、参数不合法、重复、超预算都会被拦下并写入 `state["router"]["blocked"]`；
- **任何异常都回落为空选择**，诊断主流程不因路由失败而中断；
- **预算一致**：路由调用走同一个 `_llm_tools`，计入 3 次 LLM、12k tokens、120s 的限制。

## 3. 实验设计

- **案例**：30 个，覆盖"指标可用/不可用、有/无历史报告、有/无 trace、日志厚/薄"的组合；
- **参考策略**（标签来源，事先固定）：
  1. `query_metrics`：`metrics_available` 且（`log_count<50` 或组件属于 DataNode/NameNode/JournalNode/FSNamesystem）；
  2. `search_similar_incidents`：`historical_reports_available` 且 `recurring_pattern`；
  3. `read_trace_summary`：`trace_available` 且 `log_count<100`；
  4. 多命中时按 指标 > trace > 历史 保留前 2 个。
- **四种模式**：

| 模式 | 说明 |
| --- | --- |
| `deterministic` | 不调用任何可选工具（基线） |
| `free` | 只给工具名、不给规则，JSON 输出，不校验 |
| `rules` | 给完整规则，JSON 输出，不校验 |
| `constrained` | 给完整规则 + function calling + Schema 校验 + 白名单 + 上限 |

- **模型**：`deepseek-flash`；温度 0。

> 口径说明：标签由上面的参考策略生成，**不是生产真相**。这个实验衡量的是"模型能否按规则选工具、能否给出合法参数"，不是"路由判断力有多强"。

## 4. 结果

| 模式 | 完全一致 | 精确率 | 召回率 | F1 | 多余调用率 | 漏调率 | 平均 tokens | 平均延迟 | 30 例成本 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| deterministic | 20.00% | 100.00% | 0.00% | 0.00 | 0.00% | 100.00% | 0 | 0 ms | ¥0 |
| free | 66.67% | 75.56% | 100.00% | 0.86 | 24.44% | 0.00% | 156 | 980 ms | ¥0.0122 |
| rules | **93.33%** | 96.97% | 94.12% | **0.96** | 3.03% | 5.88% | 285 | 739 ms | ¥0.0195 |
| constrained | 90.00% | 91.67% | 97.06% | 0.94 | 8.33% | 2.94% | 863 | 1030 ms | ¥0.0694 |

逐工具（命中 / 误报 / 漏报）：

| 模式 | query_metrics | read_trace_summary | search_similar_incidents |
| --- | --- | --- | --- |
| deterministic | 0 / 0 / 17 | 0 / 0 / 9 | 0 / 0 / 8 |
| free | 17 / 4 / 0 | 9 / 2 / 0 | 8 / 5 / 0 |
| rules | 17 / 1 / 0 | 8 / 0 / 1 | 7 / 0 / 1 |
| constrained | 17 / 2 / 0 | 9 / 1 / 0 | 7 / 0 / 1 |

## 5. 结论

**（1）规则写清楚，是最大的收益来源。**
同一模型、同一摘要，只把规则从"按需选择"改成可执行的判定条件，完全一致率从 66.67% 提到 93.33%，多余调用率从 24.44% 降到 3.03%。这比换框架、换模型都便宜。

**（2）function calling 没有提升准确率，但改变了失败模式。**
constrained 90.00%，略低于 rules 的 93.33%——差距来自模型对"log_count<100"这类阈值的误读（例如日志 150 条仍调 trace）。它的收益在于：

- 输出的是**结构化参数**（`{"event_id": ...}`），而不是需要下游猜的名字；
- 参数可以**被 Schema 拦截**（单测覆盖：未知工具、坏 JSON、非法字段、越界 top_k）；
- 工具集扩张时不需要重新设计输出格式。

**（3）成本是实打实的 3.6 倍。**
constrained 平均 863 tokens/例，rules 285，free 156。差额主要来自 function calling 触发的推理 token（`completion_tokens` 里含 reasoning）。延迟也从 739ms 涨到 1030ms。

**（4）因此默认策略不变。**
`agent.yaml` 仍保持 `optional_router_enabled: false`；v2 作为可选能力（`optional_router_version: v2`），只在"工具需要参数、工具集会扩张、需要审计每次选择"的场景启用。下一步是 hybrid：先用规则判定，只有规则无法覆盖时才调用模型。

## 6. 局限

- 标签由参考策略生成，存在"用规则测模型"的循环性；真正衡量判断力需要执行工具并评估下游报告质量（成本更高）；
- 30 例、单模型、单次运行，没有置信区间；
- 本轮模型没有产生非法调用，`blocked` 为 0，拦截能力主要由单测证明，而非线上样本；
- 参数错误样本偏少（模型基本都能给出合法 `event_id`）。

## 7. 复现

```powershell
# 30 例、四模式对照（需要 DEEPSEEK_API_KEY，约 ¥0.10）
python ops/scripts/evaluate_router.py --output resources/evaluation/router/result

# 只看结果表
python -c "from pathlib import Path; print(Path('resources/evaluation/router/result.md').read_text(encoding='utf-8'))"
```

产物：`resources/evaluation/router/result.json`（逐例明细）与 `result.md`（对比表）。

## 8. 面试可以这样讲（三句话）

1. "我把一个永远返回 not_available 的指标桩接成了真实查询，否则工具路由实验没有意义。"
2. "30 例对照显示：规则写清楚带来 27 个百分点提升（66.7%→93.3%），function calling 没提升准确率，但把'名字'变成了'可校验的参数'，成本是 3.6 倍。"
3. "所以我的默认仍是确定性路由，只在工具需要参数、工具集扩张时启用 function calling——这是用数据做的取舍，不是技术偏好。"
