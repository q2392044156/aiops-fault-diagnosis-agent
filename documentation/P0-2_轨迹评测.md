# P0-2：轨迹级评测实施报告

> 目标：不再只看"报告对不对"，而是看"过程合不合理"——走了几步、调了几次工具、有没有重试、证据用了多少、引用有没有落地。
> 产物：`evaluation/trajectory.py` + `ops/scripts/evaluate_trajectory.py` + 12 个单测 + 四个真实数据集的评测结果。

---

## 1. 为什么要做轨迹评测

只评最终报告会漏掉三类问题：

1. **过程错了但答案碰巧对**：工具选错、证据没用到，但模板兜底后报告看起来正常；
2. **过程对了但成本失控**：重复调用、重试、预算打满；
3. **该拒答却硬答**：没有证据仍生成"看起来有依据"的报告。

轨迹指标就是把这些问题量化，并把它们变成可回归的检查项。

## 2. 指标定义

| 指标 | 定义 | 说明 |
| --- | --- | --- |
| `steps` | 已到达的节点数 / 7 | 7 个固定节点：VALIDATED → … → REPORT_VALIDATED |
| `tool_calls` | 工具调用总数 | 含失败与重试 |
| `failed_calls` | 状态非 SUCCEEDED 的调用数 | 工具故障或超时 |
| `retries` | 同工具 + 同参数哈希的重复调用 | 反映"绕圈" |
| `evidence_coverage` | 被引用的证据 / 可用证据 | 衡量证据利用率 |
| `ungrounded_citations` | 引用了但不在证据表里的 ID | 必须为 0 |
| `token_ratio` / `active_ratio` | 预算使用率 | 超过 80% 标记预算压力 |
| `verdict` | clean / recovered / degraded / abstained / failed | 见下 |
| `flags` | 工具失败、重试、越权引用、低覆盖、无证据、预算压力、模板降级、复核过多 | 机器可读 |

**判定规则**（固定）：

- `failed`：运行失败或没有报告；
- `abstained`：报告状态为 `INSUFFICIENT_EVIDENCE`（合法拒答，不算失败）；
- `degraded`：报告降级为确定性模板；
- `recovered`：有工具失败但仍产出报告；
- `clean`：其余情况。

**pass^k**：`pass_pow_k(`…`)` 计算 k 次重复全部通过的比例（k=1 即 pass@1），用于需要重复运行的稳定性评估；本仓库的对照实验目前是单次运行，函数已实现并有单测。

## 3. 实现

| 文件 | 职责 |
| --- | --- |
| `src/evaluation/trajectory.py` | `summarize` 单次轨迹、`aggregate` 汇总、`classify` 判定、`pass_pow_k`、`markdown` |
| `ops/scripts/evaluate_trajectory.py` | 读服务 SQLite（`agent_runs` + `agent_tool_calls` + `incident_reports`），输出 JSON + Markdown |
| `tests/test_trajectory.py` | 7 个用例：干净轨迹、重试、失败恢复、模板降级、合法拒答、越权引用、预算压力、pass^k |

设计原则：**纯函数 + 数据库适配器**。核心计算不依赖数据库，便于单测；CLI 只负责查库和写文件。

## 4. 实测结果

### 4.1 30 例封存验收（framework 与 legacy 各 30 次）

| 指标 | framework | legacy |
| --- | --- | --- |
| 运行数 | 30 | 30 |
| 判定分布 | clean 18 / abstained 12 | clean 18 / abstained 12 |
| 平均步骤 | 7.0 / 7 | 7.0 / 7 |
| 平均工具调用 | 5.27 | 5.27 |
| 重试率 | 0% | 0% |
| 工具失败率 | 0% | 0% |
| 平均证据覆盖 | 90.83% | 90.83% |
| 未落地引用 | 0 | 0 |
| 问题标记 | 无 | 无 |

两条路径的轨迹完全一致——这正是 v1.1/v1.2 换框架时的核心验收目标：**换实现不能改变过程语义**。

### 4.2 离线 demo 与在线 demo

| 场景 | 判定 | 工具调用 | 证据覆盖 | tokens | 成本 | 标记 |
| --- | --- | --- | --- | --- | --- | --- |
| 离线（无 Key） | degraded | 7 | 85.71% | 0 | ¥0 | `degraded_report` |
| 在线（DeepSeek） | clean | 7 | 85.71% | 6,222 | ¥0.0269 | 无 |

离线跑出 `degraded` 是预期行为——它本来就不调用模型；在线跑出 `clean` 说明报告链路、证据引用与预算都正常。同一套指标能区分两者，说明判定逻辑有效。

### 4.3 12 次合法拒答

30 例中有 12 例是"证据不足、拒绝作答"（`INSUFFICIENT_EVIDENCE`）。它们被判定为 `abstained` 而不是 `failed`，并且不触发 `no_evidence` 标记——**拒答是能力，不是缺陷**。这个区分很重要，否则"越敢答"的系统看起来越好。

## 5. 发现了什么

1. **没有发现过程性问题**：0 重试、0 工具失败、0 越权引用，说明当前的确定性编排在 30 例验收上是稳定的。
2. **证据覆盖 90.83%**：少数用例只引用了部分证据，属于正常（一条证据可能支撑多个结论，不必全部引用）。
3. **离线/在线差异被准确识别**：同一份报告在离线时是 `degraded`，在线时是 `clean`。
4. **拒答与失败被分开统计**：12 次拒答没有被误判成失败。

## 6. 局限

- 当前数据集里没有"工具失败后恢复"和"重试绕圈"的真实样本，这两类判定目前由单测覆盖，尚未在真实数据上出现；
- pass^k 需要同一案例重复运行 k 次，现有验收是单次运行，函数未在真实数据上启用；
- 轨迹指标衡量"结构合理"，不衡量"结论正确"——后者仍需要真实根因标签（路线 A）。

## 7. 复现

```powershell
# 对任意服务数据库计算轨迹指标
python ops/scripts/evaluate_trajectory.py --database runtime/v12/service.sqlite3 --output resources/evaluation/trajectory/result

# 查看结果
type resources/evaluation/trajectory/result.md
```
