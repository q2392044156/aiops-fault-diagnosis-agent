# 发布校验策略

项目里有两类哈希，用途完全不同，不要混在一起谈。

## 1. 身份指纹（发布清单）

`digest(path)` 算文件 SHA-256，`key(obj)` 算规范化 JSON 的 SHA-256（`src/aiops_diag/common.py`）。清单把源码、配置、依赖、协议、评测集、知识库资产钉在一起，`release_id` 由清单内容派生，因此改任何一项都会换 id。

两档校验：

| 模式 | 校验范围 | 用在哪 |
| --- | --- | --- |
| 默认（日常运行） | 知识库与数据资产（`online/knowledge/release.py` 的 `verify`）+ 清单自洽性 | 服务启动、worker、本地开发 |
| 严格（发布/门禁） | 上述 + 源码、配置、依赖、部署文件重算比对 | `publish()`、`verify.strict_source: true` |

开关在服务配置顶层：

```yaml
verify:
  strict_source: false   # 日常运行；发布门禁改成 true
```

没有这一节等价于 `false`。运行期入口是 `aiops_diag/platform/runtime.py` 的 `_strict_source(cfg)`，它会传给 `verify_v11`、`verify_framework`、`verify_v12`。

源码清单一律由 `aiops_diag.common.source_files(root, *patterns)` 按 glob 生成：任何一个模式匹配不到文件就立刻 `ValueError`。**不要手写文件路径列表**——v1.2 的历史清单就是因为手写路径在目录重构后全部失效，校验从"抓篡改"退化成"报找不到文件"。

## 2. 运行期一致性（业务哈希）

| 哈希 | 存哪 | 作用 |
| --- | --- | --- |
| `args_hash` | `agent_tool_calls` | 同诊断、同工具、同参数只允许一条记录，重放命中缓存；删掉会绕过预算并重复执行工具 |
| `report_hash` | `incident_reports`、`approvals` | 审批时比对，防止"审的是 A、批的是 B" |
| `request_fingerprint` | `agent_idempotency_keys` 等 | 重复提交同一事件不会生成第二个诊断 |

这一类**不受任何开关控制**，所有模式下都必须校验。

## 3. 重构期间怎么用

- 改代码、挪文件：保持默认（`strict_source: false`），测试与启动不受影响。
- 发布前：设 `strict_source: true` 跑一遍；同时按新目录重冻 release 清单（`publish()` 会重算全部哈希并生成新 `release_id`）。
- 重冻只做一次，放在重构收尾，中间每步都冻会立刻作废。

## 4. 行尾必须是 LF

`digest()` 算的是文件字节，CRLF 与 LF 会得到不同摘要。本仓库用 `.gitattributes` 固定 `* text=auto eol=lf`，并且**不要用会写 CRLF 的方式改文件**（Windows 上 `open(..., "w")` / `Path.write_text()` 默认把 `\n` 转成 `\r\n`；批量改写一律用二进制读写或显式 `newline="\n"`）。

判定方法：

```powershell
python -c "import pathlib; print([str(p) for p in pathlib.Path('src').rglob('*.py') if b'\r\n' in p.read_bytes()])"
```

输出空列表才说明工作区与 git blob 一致，重冻出来的清单才在别人的机器上也能通过 `strict_source: true`。

## 5. 当前冻结结果（重构收尾后）

| 层 | release 目录 | release_id | 由哪份配置发布 |
| --- | --- | --- | --- |
| v1.1 base | `artifacts/releases/agent_v11_framework_base_rc7` | `agr11_073d485a35ded709be7a1e6b` | `service_v11_framework_base_rc2.yaml` |
| framework | `artifacts/releases/framework_v12_rc7` | `agrfw_9448be8b1d264909e157fe83` | `service_framework_rc2.yaml` |
| framework | `artifacts/releases/framework_v12_rc8` | `agrfw_9001970ed909b6caa13f68f9` | `service_v12_rc1.yaml` |
| v1.2 | `artifacts/releases/v1_2_rc1_15` | `agr12_80087b7b8b1e7d442984a7d5` | `service_v12_rc1.yaml` |
| v1.1 候选 | `artifacts/releases/agent_v11_rc1_20` | `agr11_ebf3ccbb4037481652e44463` | `service_v11_candidate.yaml` |

framework 层按"从哪份服务配置发布"分开：清单里的 `service_config_sha256` 就是那份配置文件的摘要，所以**一个 framework release 只能服务一份服务配置**。`service_framework_rc2.yaml` 与 `service_v12_rc1.yaml` 因此各指向自己的 framework release（rc7 / rc8），这不是重复冻结。

`artifacts/` 不进 git（体积与可重建性），换机器后按 `python -m online.diagnosis ... publish` 重新生成即可；清单里记录的源码与资产摘要来自仓库内容，因此换机器只要行尾是 LF，重算结果一致。
