# P1-4：可观测性（trace / span）实施报告

> 目标：让每一次诊断都能回答"时间花在哪、哪次调用失败、为什么重试"。
> 产物：SQLite 中的 `trace_spans` 表、引擎自动埋点、`/diagnoses/{id}/trace` 接口、Streamlit 调用瀑布。

---

## 1. 实现内容

| 组件 | 功能 | 文件 |
| --- | --- | --- |
| 追踪核心 | `Tracer` / `Trace` / `SpanRecord`，写入 SQLite | `platform/tracing.py` |
| 存储 | `trace_spans` 表 + subject 索引 | `platform/db.py` |
| 引擎埋点 | 节点、工具、LLM 调用自动记录；失败静默降级 | `diagnosis/agent.py` |
| API | `GET /api/v1/diagnoses/{id}/trace` 返回 span 列表 | `platform/api.py` |
| UI | Streamlit「调用瀑布」展开面板 | `platform/streamlit_app.py` |
| 客户端 | `ApiClient.trace()` | `platform/ui_client.py` |
| 测试 | 3 个用例：落库、父子关系、空实现 | `tests/test_tracing.py` |

## 2. Span 模型

```json
{
  "span_id": "6c5fb5...",
  "parent_id": "2d284c...",
  "name": "tool.generate_incident_report",
  "kind": "tool",
  "started_at": "2026-10-28T10:12:03.512+00:00",
  "duration_ms": 6612.2,
  "status": "ok",
  "attributes": {"tool": "generate_incident_report", "reused": false, "attempts": 1}
}
```

- `kind`：`node` / `tool` / `llm`；
- `status`：`ok` / `error` / `reused` / `yielded`；
- `parent_id`：节点之间串成链，工具与 LLM 挂到当前节点下；
- `attributes`：工具名、是否复用、重试次数、tokens、费用、stage 等。

## 3. 埋点位置

| 位置 | span | 记录内容 |
| --- | --- | --- |
| `_save` | `agent.node` | 节点名、耗时、工具数、LLM 次数、tokens |
| `_invoke` | `tool.<name>` | 工具、是否复用、重试次数、ok/error |
| `_llm` | `llm.call` | stage（router/report/repair）、tokens、费用 |
| `_llm_tools` | `llm.call` | 路由阶段同样的字段 |

## 4. 实测：一次在线诊断的 29 个 span

```text
agent.node                       6731.3ms yielded
  tool.generate_incident_report  6612.2ms ok
    llm.call                     6589.6ms ok
agent.node                        284.9ms yielded
agent.node                        118.5ms yielded
  tool.detect_anomaly              86.6ms ok
```

统计：6 个节点 span、22 个工具 span、1 个 LLM span；报告 `provenance.trace_id` 与 trace 一致。

两个值得注意的现象：

1. **reused 工具占比高**：Agent 每完成一个节点就主动让出 worker，恢复时重放前面的工具调用，全部命中缓存（`status=reused`，耗时 0ms）。这在瀑布里一眼可见，也解释了为什么"恢复不会重复付费"。
2. **生成阶段占绝对大头**：6.6 秒里 6.59 秒是模型生成，其余工具加起来不到 300ms——优化应该投向模型，而不是工具。

## 5. 设计决策

- **写 SQLite 而不是接 APM**：项目已经有单一真相源，不引入 Jaeger/OTel 依赖；需要导出时再写适配层。
- **失败静默**：span 写入异常不影响诊断主流程。
- **不记录敏感内容**：只记工具名、tokens、费用、stage，不记参数与证据正文。
- **保留 reused span**：它是"断点恢复是否真的复用"的直接证据，UI 默认展示但可折叠。

## 6. 局限

- 只在单进程内传播，没有跨 worker 的分布式 trace；
- 没有 OpenTelemetry 导出，接入现有 APM 需要再写一层；
- reused span 会让瀑布变长，目前靠 status 区分，未做聚合；
- 采样策略固定为全量，高并发下需要按比例采样。

## 7. 复现

```powershell
python demo/run_demo.py --online --keep
# 打开 demo/.runtime/service.sqlite3，查询 trace_spans 表
# 或启动服务后访问 GET /api/v1/diagnoses/{id}/trace
```

样例数据：`documentation/results/trace_demo.json`（29 个 span）。

## 8. 面试可以这样讲

1. "每次诊断都有 trace：节点、工具、LLM 调用都有 span，报告里带 trace_id，可以回放到具体哪一秒、花了多少 token。"
2. "从瀑布能直接看出 6.6 秒里 6.59 秒是模型生成，工具不到 300ms——优化方向不是拍脑袋。"
3. "恢复重放的工具调用全部标记为 reused、0ms，这就是'断点恢复不会重复付费'的可视化证据。"
